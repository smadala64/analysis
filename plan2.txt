ROLE
You are a data analyst on a healthcare call-center AI project. The data contains PHI/PII. Process it only in this approved environment. Never send raw names, member IDs, addresses, phone numbers, or DOBs to any external service. Compute every number in code; never estimate.

BUSINESS PROBLEM
Customer service representatives (CSRs) log grievances (complaints about the plan or its providers, per CMS criteria). A production AI also reads every call and flags candidate grievances. A second-stage AI adjudicator then reviews each AI flag and marks it retain, dismiss, or uncertain, applying the same CMS criteria. The production AI flags roughly 10x more grievances than CSRs log. Leadership wants to understand why: is AI over-detecting, are CSRs under-detecting, or both?

THREE DETECTION SETS (label every result with which comparison it answers)
- CSR: CSR Grievance2 = TRUE (CSR Grievance is a free-text note; nonblank note = CSR flagged)
- PROD-AI: AI Grievance = TRUE (Candidate Grievance holds the AI's text)
- ADJUDICATOR: Adjudicator Decision in {retain, dismiss, uncertain}
Comparisons: (1) CSR vs PROD-AI, (2) CSR vs ADJUDICATOR-RETAINED, (3) PROD-AI vs ADJUDICATOR.
Define RETAINED as Adjudicator Decision = retain. Report "uncertain" separately everywhere; never fold it into retained unless a result explicitly says "retain+uncertain".

INPUT
Excel file: <PATH_TO_FILE>, one row per AI detection, one month of calls. Expected columns:
Case ID, Transcript ID, Interaction ID, Call Date, CSR / Owning User, Detection ID, Detection Type, Candidate Grievance, Triggering Passage, AI Summary, Full Simplified Transcript, Decision, Reason Code, Evidence, Criterion, Rationale, Additional Review, CSR Grievance, Model, Response ID, Processed At, Request Seconds, Error, CSR Grievance2, AI Grievance, Adjudicator Decision, AI False-Positive, Adjudicator Grievance, Adjudicator False-Positive
If columns differ, stop and report the differences before continuing.

STEP 1 – COHORTS
For every adjudicated row: CSR flag (T/F) × Adjudicator Decision. Build:
- AGREE: AI=T, CSR=T, retain
- GAP: AI=T, CSR=F, retain
- UNCERTAIN_CSR_F / UNCERTAIN_CSR_T
- DISMISSED_CSR_F / DISMISSED_CSR_T
- UNADJUDICATED (Error rows), split by CSR flag
Report a full crosstab for the month and per week. Confirm the row totals reconcile before moving on.

STEP 2 – DE-IDENTIFY
Before any LLM step, de-identify Candidate Grievance, Triggering Passage, AI Summary, Evidence, Rationale, CSR Grievance notes, and Full Simplified Transcript with deterministic local code: regex for member/record IDs, phone numbers, emails, DOBs, dates of birth, street addresses/apartment numbers, ZIPs; NER for person names if a local model is available; plus a dictionary mask: any capitalized token whose lowercase form is not in /usr/share/dict/words (and is not a tag or a known plan/product/medical term) becomes [NAME?]. Replace CSR / Owning User with an HMAC pseudonym. Write 5 random de-identified rows (the fields that will go to the LLM) to deid_review_sample.txt for my review. Do not print PHI in chat. Wait for my OK before Step 3.
LLM input in later steps is limited to: pseudonymized Case ID, Candidate Grievance, Triggering Passage, Reason Code, Criterion, Rationale, Evidence, Additional Review, CSR Grievance note (de-identified). Send Full Simplified Transcript only when a row cannot be classified without it, and only de-identified.

STEP 3 – BUILD ONE CATEGORY LIST FROM THE WHOLE MONTH
- Sample ~150 rows stratified across AGREE, GAP, DISMISSED, UNCERTAIN (and across weeks). From the sample, derive 6–12 mutually exclusive grievance categories describing WHAT the caller complained about (e.g. provider office conduct, cannot find in-network provider, plan phone/agent service, treatment quality, account/enrollment/ID card, claims/authorization handling). Each category gets a one-line definition plus inclusion and exclusion rules. "Other" must be <10%; refine if larger.
- Classify EVERY adjudicated row (all cohorts) into the list. Also record for each row: a plain-language "complaint sub-type" (short phrase) and whether the complaint was the main purpose of the call or raised in passing during another request (MAIN / IN_PASSING / UNCLEAR).

STEP 4 – ANSWER THE CORE QUESTION: TYPE OF COMPLAINT, OR WAY IT IS SAID?
A. Category comparison (comparisons 1 and 2). Per category: PROD-AI count, RETAINED count, CSR count, CSR capture rate vs PROD-AI, CSR capture rate vs RETAINED, dismiss rate. Rank categories by CSR capture rate. State clearly whether CSRs concentrate on certain categories or log evenly across them, with a chi-square or equivalent test and a note on sample size.
B. Language comparison (local Python only, no LLM). In de-identified transcripts, count calls containing explicit complaint language: complaint, grievance, file a complaint, formal, supervisor, manager, escalate, report, unacceptable, not happy, upset, frustrated, dissatisfied, and variants. Compare the % of calls per term across AGREE vs GAP vs DISMISSED. Also compare MAIN vs IN_PASSING rates across AGREE vs GAP. Run a simple logistic regression or equivalent: does explicit complaint language predict CSR logging after controlling for category?
C. Within AGREE, summarize what CSR notes have in common (phrasing, whether the caller asked to file a complaint, whether the CSR states it will be logged).
Conclusion for this step, in one paragraph: the gap is mainly explained by (i) category, (ii) explicit language, (iii) complaint raised in passing, or (iv) something else, with the supporting numbers.

STEP 5 – PRODUCTION AI VS ADJUDICATOR (comparison 3)
- Dismiss rate overall, per week, per category. Summarize Reason Code and Rationale for dismissals: what kinds of AI flags does the adjudicator reject, with counts.
- For the CSR-flagged rows the adjudicator dismissed or marked uncertain: list them (de-identified) with the adjudicator's reason. These are possible adjudicator misses.

STEP 6 – OPEN-ENDED DISCOVERY
Independently of the steps above, examine the de-identified data and propose up to 5 hypotheses for why CSRs log fewer grievances than AI that we have not considered (examples only: call length, where in the call the complaint appears, issue resolved during the call, specific CSRs or days, caller type, repeat callers, calls with multiple issues). Test each with counts or rates where the data allows. Report each as SUPPORTED / NOT SUPPORTED / UNTESTABLE with the evidence. Flag any per-CSR findings as sensitive; report them by pseudonym only.
